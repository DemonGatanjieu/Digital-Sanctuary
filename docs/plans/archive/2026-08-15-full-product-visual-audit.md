## 0. 给 Gemini 的开场指令

请完整阅读本文件后再行动。你被授权调用完成审计所需的更多工具，包括 Shell、Electron/CDP、浏览器调试、截图、图片查看、DOM/CSS 检查和本地测试工具；但不得泄露用户数据、不得上传本地画廊图片、不得把真实 Pixiv 账号信息写入报告。

本任务必须执行“**基线留证 → 全量审计 → 问题登记 → 分批修复 → 同场景复测 → 文档收口**”的闭环。

禁止做完检查后只在聊天里总结。所有结论、证据和未解决问题都必须落入仓库。禁止因为问题暂时难修就删掉或不记录。禁止一次性大改后用一句“看起来正常”宣布完成。

先只完成第 1～4 阶段的审计与报告，提交审计基线后停止，等待用户确认优先级。**未经确认，不进入批量修复。**

## 1. 为什么需要这次审计

应用已经具备画廊、相册、作者馆藏、灯箱、3D/画册式展示、模型整理、AI 视觉雷达、主题、显示性能档位、探索页和设置中心。单独功能越来越完整，但视觉代码分散在多个组件与二十余个样式文件中，最近又连续加入了主题、相册和 AI 组件。

本次不是单纯寻找“哪里不好看”，而是回答以下问题：

1. 用户第一次打开时是否知道该看哪里、该点哪里；
2. 不同页面是否像同一个产品，而不是拼起来的多个 Demo；
3. 图片是否始终是视觉主角，周围环境是否起到衬托而非抢夺注意力；
4. 按钮、卡片、弹窗、导航和反馈是否符合自然操作习惯；
5. 900×620 最小窗口到 1920×1080 大窗口是否都可用；
6. 四套主题与三种显示档位是否保持信息层级和可读性；
7. 空、少量、大量、加载、失败、缺图和超长文本状态是否都被设计过；
8. 视觉效果是否以卡顿、重复解码、滚动抖动或不可控动效为代价；
9. 每个发现的问题能否被复现、修复、验证和长期保留。

## 2. 绝对规则：避免“看完就扔”

### 2.1 每个问题必须有生命周期

每个问题使用稳定编号：`VA-001`、`VA-002`……，并且只能处于以下状态之一：

- `observed`：截图中发现，尚未稳定复现；
- `confirmed`：有明确路径、尺寸和状态可以复现；
- `fixing`：已经进入某个修复批次；
- `verified`：相同场景复测通过，并有 after 证据；
- `deferred`：明确延后，写明原因、风险和建议阶段；
- `known-issue`：无法安全解决，已转入 `docs/known-issues/`；
- `not-a-bug`：经产品语义核对后关闭，必须记录理由，不能直接删除记录。

任何问题都不能从表格里消失。关闭只能改变状态并补充证据。

### 2.2 先完整审计，后批量修复

第一轮审计期间，不允许看见一个问题就改一处 CSS。否则后面的截图失去统一基线，也容易出现“修 A 坏 B”。

唯一例外：P0 导致应用完全无法启动或无法继续截图。此时先登记 `VA-xxx`，保存故障证据，做最小恢复，并单独提交。

### 2.3 不能只写聊天总结

审计必须生成以下持久化产物：

```text
docs/reviews/visual-audit/2026-08-15/
  README.md                  # 结论、基线、范围、最终状态
  coverage-matrix.md         # 页面 × 状态 × 尺寸 × 主题覆盖
  issues.md                  # VA 问题主账本
  style-system-findings.md   # 设计系统和 CSS 架构发现
  evidence/
    before/                  # 精选基线证据
    after/                   # 与问题一一对应的复验证据
```

批量原始截图可放在 `.tmp/visual-audit/2026-08-15/`，但完成审计前不得删除。最终至少把所有 P0/P1、具有代表性的 P2/P3 以及每类通过状态的精选截图放入 `evidence/`。避免提交大量重复或包含隐私的截图。

### 2.4 完成不是“代码能构建”

一个问题只有同时满足以下条件才能标记 `verified`：

1. 原复现路径已经重新执行；
2. 有对应 after 截图或可重复的自动断言；
3. 邻近页面/尺寸/主题没有出现明显回归；
4. `npm.cmd run verify` 通过；
5. `issues.md` 已更新状态、修改文件和验证方式。

## 4. 工具使用要求

不要把工具限制成“读源码 + 猜 UI”。至少使用以下四层证据：

### 4.1 静态检查

- 检查 React 页面层级、导航状态和主要 CSS 来源；
- 检查硬编码颜色、尺寸、阴影、圆角、z-index、动画和重复组件；
- 检查主题 token 与组件局部颜色是否冲突；
- 检查明显的 overflow、固定宽高、绝对定位和过长选择器；
- 检查同一种行为是否存在两套视觉实现。

静态搜索只能发现嫌疑，不能单独证明视觉缺陷。

### 4.2 Electron + CDP 自动巡视

优先复用项目现有 Electron CDP 基础，不要为了截图先引入大型测试框架。可以新增：

```text
scripts/visual-audit.mjs
```

建议能力：

- 创建隔离临时数据库和 fixture 图片；
- 用 `--remote-debugging-port` 启动构建后的 Electron；
- 用 CDP 导航/点击/输入/检查 DOM；
- 调整窗口 bounds；
- 等待字体、图片和动画稳定；
- `Page.captureScreenshot` 保存 PNG；
- 记录 console error、未加载图片、横向溢出、遮挡和不可见焦点；
- 退出后只清理临时 userData，不清理审计证据。

如 CDP 对某些原生窗口操作确实不足，可以使用已具备的浏览器/GUI/截图工具。新增依赖前先在报告写明现有工具为何不能完成，并保持为 dev-only。

### 4.3 图片逐张审阅

生成截图不等于完成审计。必须实际使用图片查看/视觉理解工具打开每张纳入 coverage 的截图，并从以下角度评价：

- 第一视觉焦点；
- 层级、间距与对齐；
- 图片与容器比例；
- 信息密度和留白；
- 按钮可发现性与危险操作区分；
- 颜色、对比度、阴影、边界和主题一致性；
- 截断、重叠、滚动条、空洞区域和视觉噪音；
- 加载、错误、选中、禁用和进度状态。

禁止根据文件名假装已经看过图片。

### 4.4 DOM 与运行时数值

对截图中的疑点用运行时数据确认，例如：

- `document.documentElement.scrollWidth > clientWidth`；
- 图片 `naturalWidth === 0`；
- 弹窗/菜单超出 viewport；
- 可点击元素尺寸小于建议触控面积；
- 元素被透明层覆盖；
- 焦点落在视口外或没有可见轮廓；
- 页面有多个互相竞争的滚动容器；
- console error / unhandled rejection；
- 长任务期间主线程明显卡顿。

自动阈值是线索，不要机械地把每个小图标都判为缺陷；结合语义和截图判断。

## 5. 确定性审计数据集

不要只用两张 1×1 PNG。fixture 至少包括：

1. 横图、竖图、方图、超长竖图；
2. 透明 PNG、普通 JPEG、WebP；
3. 单页作品和 2～5 页作品；
4. 超长中文标题、日文标题、英文标题、Emoji；
5. 长作者名、缺失作者、缺失头像；
6. 有分类、无分类、多分类；
7. 喜欢/未喜欢、选中/未选中；
8. 已生成技术视觉画像、外部 AI 解读失败、无分析结果；
9. 缺失缩略图、文件丢失或损坏的可控记录；
10. 至少 60 个作品用于观察瀑布流、懒加载、滚动和批量选择；
11. 空图库和只有 1 个作品的极端状态。

fixture 图片应由本地脚本生成简单几何图案和渐变，不使用用户图片，也不下载网络素材。每张图片必须有可辨认编号，方便从截图看出裁切、排序和重复问题。

- 确认框；

- 下拉菜单；

### 6.2 窗口与缩放

必测 CSS viewport：

| 编号 | 尺寸 | 目的 |
| --- | --- | --- |
| W1 | 900×620 | BrowserWindow 当前最小尺寸；重点检查横向溢出 |
| W2 | 1280×720 | 常见小屏/宽屏高度不足 |
| W3 | 1440×900 | 产品默认设计基线 |
| W4 | 1920×1080 | 最大化和留白/密度 |

如工具允许，再测 Windows 125% 显示缩放。注意当前 `body` 存在 960px 最小宽度，而 BrowserWindow 最小宽度为 900px，这只是一个高风险线索，必须在 W1 实际验证并登记结果。

### 6.3 主题与显示档位

内置主题：

- `default`；
- `sakura-dream`；
- `cyber-deck`；
- `hollow-zero`。

显示档位：

- `quality`；
- `balanced`；
- `efficient`。

避免无意义地执行所有排列组合：

1. 所有一级页面：`default + balanced + W3`；
2. 画廊、灯箱、设置：四套主题各测 W2/W3；
3. 画廊 60+、相册 3D/影院、探索：三种显示档位各测一次；
4. W1/W4：至少覆盖画廊、设置、相册详情和灯箱；
5. 发现某主题或档位特有问题后，扩展到受影响页面。

### 6.4 键盘、动效与无障碍视觉

- Tab 顺序和可见焦点；
- Enter/Space 激活按钮；
- Esc 关闭最上层浮层；
- 方向键用于灯箱翻页时不意外滚动背景；
- `prefers-reduced-motion: reduce` 下无强制惯性、缩放或长过渡；
- 文本对比度、禁用态仍可辨认；
- 不以颜色作为唯一状态提示；
- 200% 页面缩放下主要任务仍能完成；
- 自定义主题不能抹掉焦点、错误和危险操作样式。

## 7. 视觉评价维度

每个一级页面在报告中按 1～5 分评分，并附一句证据。分数用于发现系统性问题，不用于自我宣传。

| 维度 | 关注点 |
| --- | --- |
| 视觉层级 | 第一焦点是否明确，主次操作是否自然 |
| 图片呈现 | 裁切、比例、背景、留白是否衬托作品 |
| 一致性 | 按钮、圆角、阴影、卡片、弹窗是否同源 |
| 信息密度 | 是否过挤、过空、统计和说明是否抢夺注意力 |
| 操作可发现性 | 用户是否能猜到点击、长按、菜单和返回行为 |
| 状态反馈 | loading/success/error/disabled/partial 是否清楚 |
| 响应式 | 小窗口与大窗口是否都稳定 |
| 可访问性视觉 | 焦点、对比、减少动态、键盘状态 |
| 感知性能 | 首屏、滚动、图片切换和动效是否顺滑 |
| 品牌完整度 | 是否优雅、轻盈、二次元但不过度装饰 |

评分不是验收替代物。即使平均分高，只要存在 P0/P1，仍不能宣称审计完成。

## 8. 问题优先级和格式

### 8.1 优先级

- **P0**：页面不可用、内容不可见、无法返回、弹窗挡死、数据/危险操作误导、严重隐私视觉泄露；
- **P1**：核心流程明显别扭、重要按钮不可发现、图片普遍裁坏、最小窗口严重溢出、主题导致不可读；
- **P2**：局部层级、间距、一致性、状态反馈、键盘或动效问题；
- **P3**：精修建议，不影响完成任务。

不要把所有问题都写成 P1，也不要因为容易修就提高优先级。

### 8.2 `issues.md` 单条模板

```md
## VA-001 · [P1] 最小窗口的设置页出现横向滚动

- 状态：confirmed
- 区域：设置 / 应用壳层
- 基线：<commit>
- 环境：default / balanced / 900×620 / Windows 125%
- 复现：设置 → 外部视觉服务 → 展开自定义 Endpoint
- 期望：内容在主区内换行，只有页面纵向滚动
- 实际：body 产生横向滚动，保存按钮移出视口
- 证据：`evidence/before/VA-001.png`
- 运行时证据：`scrollWidth=...`, `clientWidth=...`
- 推测根因：只写到可验证的代码/CSS 位置；不确定就写待确认
- 修复范围：待定
- 回归邻域：画廊顶栏、相册编辑、API Key 表单
- 处理记录：
- After 证据：
```

问题标题必须描述用户现象，不要只写“CSS 有问题”。

## 9. CSS 与设计系统专项审计

在 `style-system-findings.md` 中回答：

1. 哪些颜色、圆角、阴影、间距、字体尺寸没有使用 token；
2. 哪些同类按钮/卡片/弹窗存在重复实现；
3. 是否仍有 legacy 样式影响新组件；
4. 同一状态是否用多个 class/命名体系表达；
5. 主题是否只改颜色，还是错误地改变布局和可用性；
6. `z-index` 是否形成可解释层级；
7. 哪些固定高度/宽度在 W1/W2 产生问题；
8. 哪些动画在 efficient 或 reduced-motion 下仍运行；
9. 图片容器是否统一处理 `object-fit`、加载占位和错误状态；
10. 是否存在两套灯箱、两套通知、两套按钮等维护分叉。

不要在审计阶段直接把全部 CSS 合并成一个文件。报告应提出分批重构边界，例如：

- Batch A：token 与基础组件；
- Batch B：壳层/导航/响应式；
- Batch C：画廊/卡片/灯箱；
- Batch D：相册/作者；
- Batch E：设置/模型整理/外部视觉；
- Batch F：主题覆盖与动效。

每批都要可独立回滚。

## 10. 执行阶段与停点

### Phase 1：基线与自动审计工具

- [ ] 记录 Git 基线和工作区状态；
- [ ] 运行 `npm.cmd run verify`；
- [ ] 创建审计目录和 coverage 模板；
- [ ] 建立隔离 fixture 数据集；
- [ ] 建立/扩展 CDP 截图脚本；
- [ ] 证明脚本不会使用或改写真实 userData；
- [ ] 生成第一张可复现截图。

若 verify 在审计前已经失败，登记为阻塞问题，不得将失败归咎于审计工具后继续假装完成。

### Phase 2：全量基线截图与运行时检查

- [ ] 按覆盖矩阵执行；
- [ ] 截图命名包含页面、状态、主题、尺寸；
- [ ] 收集 console、图片加载、overflow、焦点和浮层数据；
- [ ] 每个格子填写 pass/issue/blocked/N/A；
- [ ] 不做批量视觉修复。

### Phase 3：逐图审阅与问题登记

- [ ] 实际打开每张纳入覆盖的截图；
- [ ] 给所有问题分配 VA 编号；
- [ ] 合并同根因重复现象，但列出所有受影响页面；
- [ ] 写 `style-system-findings.md`；
- [ ] 形成 P0/P1/P2/P3 总表；
- [ ] 无法复现的观察保留为 observed，不删除。

### Phase 4：审计基线提交并停下

- [ ] `git diff --check`；
- [ ] 确认无隐私和无大批重复截图；
- [ ] 提交审计工具、fixture、报告和精选 before 证据；
- [ ] 在最终消息中列出 P0/P1 数量、前三个系统性根因和推荐修复批次；
- [ ] **停止，等待用户确认。**

到这里是本轮默认授权范围。不要自行进入 Phase 5。

### Phase 5：按确认顺序分批修复

只有用户确认后开始。每个批次：

1. 在 `issues.md` 标注包含的 VA 编号；
2. 保存 before 证据；
3. 做最小、同根因修复；
4. 不趁机重写无关页面；
5. 重跑目标矩阵和邻近回归；
6. 保存 after 证据；
7. 运行 `npm.cmd run verify`；
8. 更新问题状态；
9. 独立提交。

### Phase 6：最终视觉回归

- [ ] 重新执行完整核心矩阵；
- [ ] 核对所有 verified 问题的 before/after；
- [ ] 未解决项转 deferred 或 known issue；
- [ ] 更新评分和最终结论；
- [ ] 确认没有新增 P0/P1；
- [ ] 运行 `npm.cmd run verify`；
- [ ] 提交最终审计报告。

## 11. 禁止事项

- 禁止只读源码、不启动应用就宣布完成视觉检查；
- 禁止只生成截图、不实际查看截图；
- 禁止边审计边无记录地随手改样式；
- 禁止用 `!important`、全局缩放或隐藏 overflow 掩盖根因；
- 禁止用降低字号解决所有拥挤问题；
- 禁止为了视觉统一破坏作品信任、下载、导航或数据语义；
- 禁止删除难修问题或把它们从报告中移除；
- 禁止用“构建通过”代替视觉复测；
- 禁止把真实用户图库复制到 fixture；
- 禁止把真实账号、Cookie、API Key 和远程图片写入证据；
- 禁止一次提交混合审计工具、全局 CSS 重构和多个无关功能；
- 禁止修改/删除已有 known issue 来制造“全部完成”；
- 禁止未经用户确认自行执行 Phase 5 批量修复。
