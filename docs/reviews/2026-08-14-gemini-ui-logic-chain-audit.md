# Gemini 新设计交互链路审计（2026-08-14）

> 面向下一轮 Gemini 修改。请先修闭环与数据语义，再继续增加视觉效果。

## 1. 结论先行

这一轮的视觉方向本身有价值：主题、影院预览、画册式相册、组合视图和指南针都已经形成了鲜明记忆点。当前的主要问题不是“不够好看”，而是多个设计分别成立，组合后却共用不了同一套导航、数据对象、信任规则和操作反馈。

建议立即暂停新增视觉概念，按以下顺序收口：

1. 恢复可类型检查的代码基线。
2. 修通相册入口、返回和批量加入的完整链路。
3. 统一作品级数据模型与“主动下载即可信”的画廊展示规则。
4. 明确“分类 / 智能视图 / 画集相册”三者的产品边界。
5. 再整合主题指南针、影院预览、外部链接、动效和无障碍。

当前不宜继续把路线图标成“全部完成”。它会掩盖实际断点，也会让后续模型把错误基线继续当成事实。

## 4. P0：必须先修的链路

### P0-1：恢复真实的验证门禁

证据：

- `CollectionGallery.tsx:126` 使用不存在的 `ArtworkSource.pageCount`。
- `GalleryView.tsx:227` 向 `SavedCollectionViewCard` 传入不存在的 `onDelete` 属性。
- `InteractiveCompassDial.tsx` 有多处 `undefined` 未收窄错误。
- `WorkLibrary.tsx:585` 使用了未导入的 `useCallback`。

要求：

1. 修复错误本身，不允许使用 `any`、`@ts-ignore` 或放宽 `strict`。
2. 新增统一的 `verify` 命令，至少顺序执行 `typecheck`、`test`、`build`。
3. 路线图或快照只能在 `verify` 通过后写“完成”。
4. 给这次暴露的四类问题补最小测试，特别是相册入口和作品级批量加入。

验收：

- `npm.cmd run typecheck` 返回 0。
- `npm.cmd test` 返回 0。
- `npm.cmd run build` 返回 0。
- CI 或本地统一命令不会再出现“构建通过但类型检查失败”的假绿。

### P0-2：相册详情是死路由，精装画册设计当前不可达

证据：

- `GalleryView.tsx:86` 声明了 `selectedCollectionId`。
- `GalleryView.tsx:174-181` 只有在 `selectedCollection` 存在时才渲染 `CollectionDetailPage`。
- 但文件中没有任何入口调用 `setSelectedCollectionId(collection.id)`。
- `GalleryView.tsx:259-267` 的相册卡片点击行为是设置 `workQuery.collectionId`，随后切到 `flat`。

因此当前用户点击一本“画册”后，只会看到普通平铺筛选；精装封面、卷首题记、目录索引、网格模式和“从画廊添加作品”都不会出现。

建议交互：

- 单击相册卡片：进入相册详情。
- 相册卡片的次级操作或详情页按钮：“在画廊中筛选查看”。
- 返回：回到相册库，并尽量恢复原滚动位置。
- 切换侧栏后回来：至少保留当前画廊模式；是否保留详情页需形成明确统一规则。

验收：

1. 相册卡片单击能进入详情。
2. 详情中的返回按钮回到相册库。
3. 详情中的目录与网格切换均可用。
4. “平铺筛选”是独立、可发现的动作，不再冒充“打开相册”。
5. 增加一个组件/端到端测试，证明 `CollectionDetailPage` 可从正常 UI 入口到达。

### P0-3：相册仍使用旧的图片页模型，破坏“作品是一级对象”的原则

证据：

- 平铺画廊已经使用 `WorkListItem / WorkRecord`，一个多页作品只显示一张卡。
- `CollectionDetailPage`、`ArtworkCard`、`AuthorGallery` 仍使用 `ArtworkRecord`，一页就是一个对象。
- `CollectionGallery.tsx:55-56` 的“作品”和“画作”统计实际都等于 `items.length`，第二个表达式无论条件如何都只加 1。
- `CollectionGallery.tsx:126` 试图从 `ArtworkSource` 读取不存在的 `pageCount`，暴露了模型层级错位。
- `CollectionGallery.tsx:175-178` 对所选图片页逐项调用异步 `onAssign`，但不等待完成就关闭弹窗。
- 父层每次加入都会用一次返回结果覆盖 `artworks`；多个并发结果可能后到覆盖先到，用户看到“选了很多但只加进去一部分”。

不要用“补一个 `pageCount` 字段”来遮住问题。正确方向是让作者馆藏、相册详情、挑选器和影院预览都基于作品对象：

- 列表：`WorkListItem`。
- 详情/预览：按需读取 `WorkRecord.assets`。
- 相册关系：`collection_works`，一次加入整个作品。
- 批量 API：`addWorksToCollection(workIds, collectionId)`，在数据库事务中完成，并一次返回结果。

验收：

1. 多页作品在相册挑选器中只出现一张卡，并显示页数。
2. 加入相册时默认加入整部作品，不拆页。
3. “作品数”和“图片页数”口径明确且不同。
4. 批量加入失败时弹窗不提前关闭，并显示成功/失败数量。
5. 相册封面应明确绑定“作品封面资源”，不要继续依赖任意旧 `artworkId`。

### P0-4：主动下载作品的信任规则在三个浏览模式中不一致

产品基线已经在 `docs/design/PIXIV_RESOURCE_MANAGER_V2.md` 写明：收藏空间管理用户主动保存的可信作品，不因后台模型自动变模糊。

当前实现：

- 新平铺画廊 `WorkLibrary` 不应用模糊。
- `ArtworkCard.tsx:21` 在没有决定时默认 `blur`。
- `AuthorGallery.tsx:32-39` 继续根据旧审查决定隐藏或模糊封面。
- `ArtworkLightbox.tsx:232` 在影院预览中再次应用 `blurred`。

这会导致同一张主动下载的作品：平铺中清晰，切到画师馆藏后变模糊，打开某些入口的影院预览又继续模糊。

要求：

- 浏览画廊、作者馆藏、相册和影院预览时，共用一套“本地收藏展示策略”。
- 用户主动下载内容默认清晰。
- 模型整理是用户显式启动的元数据/分类能力，不反向覆盖下载信任。
- 探索页的实时元素拦截仍保持独立，不与本地收藏策略混为一谈。
- 不要只用 CSS 去掉 `filter`；应从展示策略和视图模型中消除旧逻辑分叉。

验收：同一作品从平铺、作者、相册、组合视图四个入口打开时，清晰度与信任说明完全一致。

### P0-5：查询状态跨模式泄漏，空状态可能挡住整个页面

证据：

- `GalleryView.tsx:157` 的顶部统计永远读取当前 `workResult`。
- `GalleryView.tsx:164` 在判断具体 `mode` 之前，先用 `workResult.total === 0` 决定是否显示全局空状态。
- 组合视图、普通分类点击后会改变同一个 `workQuery`。
- 切到作者或相册模式时并不会统一清理当前搜索、分类或组合条件。

后果示例：用户临时组合筛选得到 0 个作品，再切到“相册画集”或“画师馆藏”，可能先命中“画廊还是空的”，对应模式根本无法展示；即使能展示，顶部作品数也可能是旧筛选数量，而下方作者列表来自全量 `artworks`。

建议：

- 每个一级模式拥有自己的查询/导航状态。
- 全局统计使用全库摘要，当前筛选统计放在对应模式内部。
- 空状态在模式内部判断，不得用平铺查询结果阻断其他模式。
- 明确模式切换策略：保留各自上次状态，或每次回到默认；不要隐式混用。

验收矩阵：

1. 平铺筛选为 0 时仍可进入相册库和作者馆藏。
2. 相册库统计与相册列表数据源一致。
3. 作者馆藏统计与作者列表数据源一致。
4. 从组合视图进入平铺后能看见清晰的组合条件，并可一键退出。

## 5. P1：需要形成统一产品模型

### P1-1：不要再让一个 `Collection` 同时扮演分类、智能视图和艺术画册

当前 UI 同时出现：

- 顶栏“新建相册”；
- 弹窗“新建分类”；
- 页面“相册画集”；
- 区块“全部普通分类”；
- “新建相册组合 / 分类组合 / 组合视图”；
- 相册详情又拥有精装封面、卷首题记和书籍目录。

这不是单纯的文案不统一，而是三种不同产品对象被叠在一起：

1. **分类（Collection / Tag-like group）**：多对多归类，无固定顺序，适合 AND/OR/NOT。
2. **智能视图（Saved View）**：保存查询，不拥有作品，只动态展示匹配结果。
3. **画集相册（Album / Artbook）**：用户策展，拥有封面、题记、作品顺序，未来可扩展章节。

推荐的长期方案是拆实体：保留 `collections` 与 `saved_collection_views`，另建 `albums`、`album_works(position)`。如果当前阶段不愿升级数据库，则应暂时把现有对象统一叫“分类”，隐藏精装画册承诺，等真正的 Album 模型完成后再开放画册 UI。

不能接受的折中是：只把所有“分类”替换成“相册”。因为布尔组合、无序多对多关系和精装画册在用户心智上并不是一回事。

### P1-2：指南针与开放主题系统没有共用同一个主题来源

证据：

- `InteractiveCompassDial.tsx:17` 硬编码 4 个 `SECTORS`。
- 设置页允许导入本地主题，也允许安装任意社区主题。
- 当自定义主题生效时，`activeSectorId` 会变成自定义 ID，但 `activeSector` 又回退到第一项，标签与真实主题不一致。
- 用户在指南针上释放指针后，组件会直接调用 `setActiveTheme` 切回某个内置主题。
- 切换失败被忽略，没有通知；惯性动画也没有读取“减少动态”偏好。

请先做产品决策，二选一：

**方案 A（推荐）——指南针是“四套官方氛围快捷切换器”**

- 明确标注“官方氛围”，不冒充完整主题选择器。
- 自定义主题生效时显示“自定义主题”，指南针保持中立，不伪装成蔚蓝默认。
- 拖动只预览，吸附并确认后再提交切换；失败显示通知并回滚。
- 完整主题管理仍只在设置页。

**方案 B——指南针动态读取全部已安装主题**

- 扇区根据 `getInstalledThemes()` 生成。
- 需要解决主题数量变化、排序、超过合理扇区数、删除中的主题、社区主题色彩元数据等问题。

无论选哪种方案，都必须：支持键盘操作、处理 `pointercancel`、卸载时取消 `requestAnimationFrame`、减少动态时禁用惯性，并避免在拖动过程中频繁写持久化主题。

另有一个明确 CSS 错误：`styles/compass-dial.css:102` 使用 `transform: scale(1.18) !important`，会覆盖 JSX 为方位文字设置的 `rotate(...) translateY(...)`，激活文字可能脱离环形位置。缩放应使用内层元素或组合完整 transform。

### P1-3：合并两套影院预览

当前存在：

- `ArtworkLightbox.tsx`：旧图片页模型入口使用。
- `WorkLibrary.tsx:561` 内部的 `WorkLightbox`：新作品模型入口使用。

两者已有差异：旧版有图片加载失败提示，新版没有；旧版继续执行模糊规则，新版不执行；状态、快捷键和缩放逻辑已经复制两份。

建议抽成唯一 `WorkViewer`：输入作品标题、作者、资源页列表、初始页与展示策略。所有平铺、作者、相册、组合视图都调用它。

统一验收：

- 原图不存在时有可退出的错误状态。
- Esc 关闭、左右翻页、滚轮缩放、双击切换均一致。
- 打开时聚焦查看器，关闭后焦点回到原卡片。
- 缩放和平移有合理边界，不会把图片永久拖丢。
- 多页胶片轨只读取缩略图，不一次解码所有原图。
- “减少动态”偏好关闭非必要过渡和 HUD 动画。

### P1-4：可见外部链接目前都是假按钮

证据：

- `AuthorGallery.tsx:80` 用 `target="_blank"` 显示 Pixiv 作者链接。
- `ThemeSettingsSection.tsx:302` 用 `target="_blank"` 显示主题作者链接。
- `apps/desktop/src/main/index.ts:263` 对主窗口执行无条件 `setWindowOpenHandler(() => ({ action: "deny" }))`。

因此用户能看到链接样式，但点击后没有任何结果。

要求：提供主进程控制的安全外部打开 API，只允许 `https:`，Pixiv 作者入口校验 `www.pixiv.net/users/<id>`，主题作者链接至少显示目标域名。成功时由系统默认浏览器打开，失败时有应用内错误通知。不要在渲染层直接放任任意 URL。

### P1-5：异步操作需要统一的“开始—进行中—完成/失败—恢复”协议

至少覆盖：

- 相册批量加入；
- 相册封面更新；
- 主题安装、切换、删除；
- 组合视图保存、删除；
- 指南针主题切换。

统一规则：

1. 开始后锁定会产生冲突的控件。
2. 完成前不关闭弹窗或离开上下文。
3. 成功显示对象、数量和结果。
4. 部分失败显示成功/失败数量和重试入口。
5. 可撤销的操作尽量复用现有 `AppNotice` 撤销模式。
6. 删除社区主题必须确认；删除当前主题时明确说明会回退到默认主题。

## 6. P2：交互质量、性能与可维护性

### P2-1：指南针不是可访问控件

当前根元素只有指针事件和 `title`，没有按钮/滑块语义、焦点、方向键或确认方式；透明 `::before` 热区向外扩 32px，可能吞掉附近 Hero 控件的点击。

建议：

- 将指南针实现为可聚焦的自定义 slider/radiogroup，提供可读标签和当前值。
- 左右键选择、Enter 应用、Esc 取消预览。
- 给热区画调试边界做一次重叠检查，再决定 hit-slop 大小。
- 增加 `pointercancel`、窗口失焦和卸载清理。

### P2-2：“减少动态”只改 CSS，不能停止 JavaScript 惯性和计算

CSS 的极短动画时长无法阻止指南针继续每帧 `requestAnimationFrame + setState`。这会让用户开启减少动态或省电档后，风扇仍可能因为 JavaScript 和合成层工作而转。

要求：组件直接读取性能/动态偏好：

- 省电：不渲染指南针或显示静态主题按钮。
- 减少动态：无惯性、无 3D 倾斜、直接吸附。
- 卸载：取消动画帧。
- 动画中不要触发高频持久化或网络调用。

### P2-3：作者/相册模式仍按全量图片页在 React 中聚合

`buildAuthorGroups(artworks, artists)`、相册 `filter`、组合卡片 `filter` 都依赖 `listArtworks()` 返回完整图片页数组。这与 V2 文档中“作者、分类和作品查询返回视图模型，不由 React 每次遍历全库临时聚合”的方向冲突。

建议新增分页查询：

- `queryArtistsWithStats` / `queryArtistWorks`；
- `queryCollectionsWithStats` / `queryCollectionWorks`；
- `querySavedViewPreview`；
- 封面和四宫格预览由 SQL 限量返回。

不要等图库再次卡顿才迁移；当前作品级模型统一正好是合适窗口。

## 7. 推荐的信息架构

建议一级浏览结构保持简单：

| 一级入口 | 数据来源 | 主要动作 |
| --- | --- | --- |
| 画廊 | 全部 `Work` | 搜索、排序、喜欢、批量操作、打开影院预览 |
| 画师馆藏 | 按作者聚合的 `Work` | 进入画师、浏览作品、在 Pixiv 打开 |
| 分类 | `Collection` + `collection_works` | 归类、组合筛选、移出分类 |
| 画集相册 | `Album` + 有序 `album_works` | 策展、排序、封面、题记、章节（可后置） |
| 智能视图 | 保存的查询 | 临时查看、编辑条件、删除视图 |
| 模型整理 | 显式任务 | 选择范围、预览成本、开始、取消、确认建议 |

如果暂时不实现真正的 Album 数据模型，可以先不显示“画集相册”一级入口，避免视觉承诺超前于数据能力。
