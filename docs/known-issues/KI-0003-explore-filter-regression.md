# KI-0003：探索页普通作品误拦，第一方广告漏拦

- 状态：回归根因已定位，P0 代码修复完成 / 待实机复核
- 发现日期：2026-08-11
- 优先级：P0
- 相关提交：`158aa52`、`3731bb8`、`9a1962d`

## 现象

用户反馈探索页同时存在两类错误：

1. 大量正常作品被内容审查误拦，当前过滤结果不具备可接受的浏览准确率。
2. Pixiv 第一方推广仍然可见，包括：
   - 页面上方带 `PR` 标记的推广卡片；
   - `Hitenkei's Booth` 商品/合作推广卡片。

用户提供的截图已作为本次回归证据：普通作品误拦与 PR/BOOTH 广告漏拦同时出现。

## 影响

- 探索页的核心体验被破坏：正常作品被隐藏，广告仍然占据可见区域。
- 不能简单降低所有元素阈值来“修复”误拦，因为这可能放过真正的血腥、猎奇或断肢内容。
- 不能把 Pixiv 第一方图片域名整体加入网络黑名单；普通作品和广告共用 Pixiv 图片 CDN。

## 2026-08-11 根因审计

- 本机 `remote_image_reviews` 中现有 47 条真实远程审查记录全部为 `allow`，没有一条命中元素黑名单。常见推理耗时约为 417–562 ms。
- 这排除了“WD Tagger 阈值导致大批普通作品误拦”这一假设。被误拦图片没有进入审查记录，说明它们在模型之前就被取消了。
- 根因是第一方推广 DOM 适配器的宽泛猜测：它会从 `PR`、属性文本或 BOOTH/FANBOX 链接向上寻找最多九层祖先，并允许命中含最多 12 张图片、16 个链接的大容器。普通作品列表因此可能被整体标成推广。
- 适配器随后把该容器内所有 Pixiv 图片 URL 加入推广集合；主进程在内容审查之前查询这个集合并直接取消图片请求。这也解释了“页面大量被挡，但数据库仍全是放行”的矛盾。
- 适配器还被每秒重复调用一次；虽然页面内安装是幂等的，跨进程脚本调用本身仍是不必要的浏览负担。
- 当前 WD Tagger 任务已经是严格单并发，并且同时具备内存去重和 SQLite 持久缓存，不存在一次并发 30 个模型任务的实现。
- 当前 Python 环境只有 `CPUExecutionProvider`，代码也显式固定为 CPU；RTX 4050 尚未参与推理。

## P0 修复

- 删除基于 `PR` 文本、DOM 祖先层级和推广链接域名的第一方推广猜测。
- 删除每张作品在审查前执行的推广 URL 页面查询，所有作品图统一进入已有的内容审查与缓存流程。
- 删除每秒一次的 DOM 适配器轮询；保留页面导航时安装与页面内 `MutationObserver`。
- 保留被拦作品的占位层、命中原因和“仅本次查看”。
- 保留现有网络广告/跟踪器规则。第一方 PR/BOOTH 广告可能暂时重新出现，这是为了先恢复普通作品的正确显示；后续由标准广告过滤引擎处理，不再用宽泛 DOM 猜测。
- 已通过 TypeScript 类型检查、20 个 Vitest 测试和 3 个 Python 测试。

性能与第三方广告过滤的后续设计见 [`a3-explore-performance-adblock-plan.md`](../research/a3-explore-performance-adblock-plan.md)。

## 实机复核项

- 探索页普通作品不再因附近出现 `PR` 或 BOOTH/FANBOX 链接而成片消失。
- 真正命中元素黑名单的图片仍显示占位层、命中原因，并可“仅本次查看”。
- 同一图片上下滚动后优先命中缓存，不重复推理。
- 确认运行的是最新构建，并且没有旧 Electron 进程占用单实例锁。

## 暂不采取的处理

- 不恢复年龄分级过滤。
- 不把所有 Pixiv/pximg 图片放行。
- 不把 `PR` 作为普通文本子串全局匹配。
- 不在没有命中原因证据时全局调低或关闭内容规则。
