# A3：探索页流畅审查与标准广告过滤方案

- 日期：2026-08-11
- 目标：不牺牲元素拦截可靠性的前提下，让 Pixiv 瀑布流保持顺滑，并停止维护脆弱的广告 DOM 猜测。

## 实施状态

- 已完成：独立探索页 preload，在页面最早阶段保护未审查作品图。
- 已完成：`IntersectionObserver`（前后 400 px）只提交可见或即将可见的图片。
- 已完成：可见优先、同级 FIFO、URL 去重的单并发队列；离开视口且尚未开始的任务会移出队列。
- 已完成：缓存命中直接放行/拦截，未命中请求立即返回保护态，模型放行后再重载原图；不再长时间占用 Chromium 的网络回调。
- 已完成：页面结果缓存和主进程内存缓存均限制为 500 条；SQLite 持久缓存继续保留模型版本与规则指纹。
- 已完成：状态栏区分“队列”和“审查中”，控制台记录优先级、缓存来源、排队及审查耗时。
- 已回退：真实 Pixiv 会话出现 KI-0004，作品几乎全部停留在保护态；`ENABLE_VIEWPORT_REVIEW` 当前默认关闭，恢复同步审查。
- 暂缓：广告过滤引擎与 Chrome 扩展；先由 Pixiv Premium 官方广告开关处理。
- 已完成：RTX 4050 CUDA provider 独立环境与基准测试，详见 [`a4-rtx4050-gpu-benchmark.md`](./a4-rtx4050-gpu-benchmark.md)。

## 结论

用户提出的方向基本正确，但当前实现与假设有两处差异：

1. 模型队列已经是单并发，不会同时启动 30 个 WD Tagger；内存去重与 SQLite 持久缓存也已经存在。
2. 当前真正的性能问题是所有 Pixiv 作品请求都会被暂停、由主进程重复下载一次、排队完成 CPU 推理后才放行。页面滚动产生一批图片时，虽然不会撑爆显存，却会形成很长的串行网络/推理瀑布。

因此不能只把并发限制设成 3–4。CPU 路径继续单并发更合理；首先要改变“所有请求同步等模型”的管线，并让 RTX 4050 真正参与推理。

## Chrome 扩展取舍

Electron 可以向持久会话加载解压后的 Chrome 扩展，但不支持直接安装任意 Chrome 商店扩展，也不以完全兼容 Chrome 为目标。扩展不会跨启动自动恢复，需要应用每次重新加载。

本项目也已有一个覆盖全会话的 `webRequest.onBeforeRequest`，负责安全导航、广告规则与作品审查。Electron 对同一事件只使用最后注册的监听器；直接加载 uBlock/AdGuard 或直接调用第三方 Electron blocker 的自动安装函数，可能覆盖现有审查器，或者被现有审查器覆盖。

### 推荐方案

采用 `@ghostery/adblocker-electron` 作为可嵌入过滤引擎，而不是把完整 Chrome 扩展当产品依赖：

- 使用 EasyList/uBlock Origin 兼容规则，替代手写广告域名和 Pixiv DOM 文本猜测。
- 只保留一个应用级 `onBeforeRequest` 监听器；在该监听器内部先调用过滤引擎匹配，再进入作品审查逻辑。
- 使用引擎的 cosmetic filters 处理 Pixiv 第一方 PR/BOOTH 卡片；不能仅靠 CDN URL 区分它们。
- 将过滤列表和序列化引擎缓存在用户数据目录，启动时无需每次联网编译。
- 先在探索页会话启用，不影响本地画廊和认证会话。

完整 Chrome 扩展可在以后作为“实验性：加载用户提供的解压扩展”功能，但不作为默认广告拦截方案，也不承诺商店扩展兼容。

## 推荐审查管线

### 阶段 1：先测量，不猜并发

- 在每个候选图片上记录：进入队列、开始下载、下载结束、开始推理、推理结束、放行/拦截、缓存类型。
- 分离网络等待与模型耗时，统计 P50/P95。
- 状态栏只展示用户能理解的队列长度和缓存命中；详细时间写入诊断日志。

### 阶段 2：视口优先、默认模糊

- 为 Pixiv 视图增加本地 preload，在文档最早阶段给作品图片施加不可见/模糊保护样式，避免未审查图片闪现。
- 使用 `IntersectionObserver`，`rootMargin` 先设为 300–500 px，只把可见和即将可见的图片送入优先队列。
- 新图片状态为 `pending`；放行后淡入清晰图，命中后保留模糊并替换为现有占位层。
- 页面离开或图片远离视口时取消尚未开始的低优先级任务；已开始的推理不强杀。
- 主进程必须校验 IPC 发送者和 URL，远程页面不能直接获得文件或 Electron 能力。

这一步需要替换当前“在网络请求回调里一直等待 AI”的模式。单纯在现有 `onBeforeRequest` 外面加 `IntersectionObserver`，无法解除已经被暂停的网络请求，也无法解决页面卡顿。

### 阶段 3：队列与缓存

- CPU 模式保持并发 1；GPU 也先从并发 1 开始基准测试，再决定是否升到 2。固定使用 3–4 并发没有硬件依据。
- 队列顺序：已进入视口 > 一屏内预取 > 其他候选；同级按出现时间排序。
- 保留现有 `remoteReviewPending` 去重和 SQLite 持久缓存；缓存键继续包含模型版本与规则指纹，规则变化后不会复用旧结果。
- 给内存 Map 增加 LRU 上限，防止长时间浏览后无限增长。
- 不直接把同一作品的不同缩略图 URL 合并为一个“允许”结果：方形裁剪可能隐藏完整图边缘的目标元素。可以安全研究复用“拦截”结果，但“允许”仍应按实际图像版本审查。

### 阶段 4：GPU 加速

- 当前环境为 `onnxruntime==1.28.0`，只有 CPU/Azure provider；`engine.py` 还显式指定 `CPUExecutionProvider`。
- 另建可回滚的 GPU 试验环境，优先评估 NVIDIA CUDA provider；记录冷启动、单图 P50/P95、显存、结果一致性与失败回退。
- provider 优先级采用 GPU 在前、CPU 兜底；启动日志和状态栏明确显示实际 provider，不能仅凭设备上存在 RTX 4050 就宣称已启用 GPU。
- 不在当前稳定虚拟环境里直接替换 ONNX Runtime，避免为性能实验破坏可用的内容审查。

## 实施顺序

1. 已完成 KI-0003 的 P0 回归修复。
2. 已完成首版耗时日志、document-start 保护、Intersection Observer 和视口优先队列。
3. 使用真实 Pixiv 会话复核并调整保护样式、400 px 预取距离和状态栏反馈。
4. 单独完成 GPU provider 试验，达标后再进入默认运行环境。
5. 广告过滤引擎继续留在待办，除非 Premium 官方隐藏广告仍不能满足需求。

## 验收指标

- 快速滚动时 Electron 工具栏和 Pixiv 页面保持响应，不因一批图片进入队列而冻结。
- 未审查图片不会短暂清晰闪现；已放行图片不会在上下滚动时反复推理。
- 普通作品不会因广告 DOM 邻接关系被拦；第一方推广由标准过滤规则命中。
- 模型/规则改变后缓存自动失效；模型失败时继续默认保护，而不是静默放行。
