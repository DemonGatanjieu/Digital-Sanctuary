# A5：10,000 作品 Electron 画廊基准

- 日期：2026-08-14
- 命令：`npm.cmd run benchmark:library`
- 环境：Windows、Electron 43.3.0、生产构建、独立临时 `userData`
- 数据：SQLite 中生成 10,000 个元数据作品，不读取真实账号和画廊文件

## 当前结果

| 指标 | 最近实测 | 自动门禁 |
| --- | ---: | ---: |
| 首批 60 张卡片可见 | 620 ms | 5,000 ms |
| 连续 36 次触底后已加载卡片 | 1,440 | 至少 120 |
| Renderer 累计任务耗时 | 6,487.5 ms | 8,000 ms |
| 其中脚本耗时 | 3,330.2 ms | 仅记录 |
| 其中布局耗时 | 1,431.9 ms | 3,000 ms |
| 样式重算耗时 | 138.1 ms | 仅记录 |
| Renderer JS 堆 | 20 MB | 512 MB |
| 图片元素/解码 | 0 | 0 |
| 模型整理中心生产构建冒烟 | 可打开 | 可打开 |

基准通过 CDP 操作真实 Electron renderer，并使用页面实际的 `main` 滚动容器。测试环境单独关闭 Chromium 后台节流；普通产品窗口仍使用默认节流策略。

脚本仍记录空闲与滚动 rAF P95、最大帧等待以及 Long Task 数据，但这些墙钟指标会受 Windows 前台抢占和异步 React 提交时序显著影响，因此只用于人工观察趋势。自动门禁使用 DevTools 的累计任务、布局和内存指标，避免同一构建在不同前台状态下随机红绿。

## 能证明什么

- 10,000 条数据库记录不会在首屏全量传给 React，首批保持 60 条。
- 连续分页不会加载元数据 fixture 中不存在的原图。
- 渐进分页和 `content-visibility` 在中等长度连续浏览中维持有界内存。
- 构建后的样式模块不会造成数量级的脚本、布局或样式重算退化。

## 不能证明什么

- 元数据 fixture 不含真实缩略图，不能替代不同尺寸、编码和损坏图片的解码压力测试。
- 36 次触底没有把 10,000 张卡片全部留在 DOM 中；若以后支持“一次滚完整库”，应改为窗口化列表，而不是无限追加全部节点。
- 数值会随机器、显示缩放和 Electron 版本变化；门禁用于捕捉数量级回归，不作为硬件横向排名。
